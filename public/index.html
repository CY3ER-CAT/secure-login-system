The control plane

Every layer does one job well.

Authentication fails at the seams. Each control below is implemented in a separate, testable layer — not bolted on after the login form.

Credential hashing

bcrypt with a unique salt and a configurable work factor. Plaintext passwords never touch the database, logs, or API responses.

bcrypt · 12 rounds

Server-side sessions

A signed, HttpOnly cookie carries only a session ID. Session data lives server-side, the ID is regenerated at sign-in, and logout destroys it completely.

HttpOnly · SameSite

Request integrity

Synchroniser-token CSRF protection on every state-changing request, paired with a strict Content Security Policy and hardened response headers.

CSRF · CSP · Helmet

Two-factor, stored properly

Enroll with a QR code, verify with a six-digit TOTP, and keep secrets encrypted at rest with AES-256-GCM. Recovery codes are single-use and hashed.

TOTP · AES-256-GCM

Abuse resistance

Per-IP and per-identifier login limits, temporary account lockout, generic authentication errors, and a dummy bcrypt comparison for unknown accounts.

rate limit · lockout

Data integrity

Every query is parameterized. Schema constraints and case-insensitive unique indexes keep identity data consistent under concurrency.

SQLite · prepared statements

Defense in depth

Trust is a stack, not a checkbox.

A request passes through independent controls before it reaches the database. If one layer is bypassed, the next one still has a job to do.

How it works

Three steps. No shortcuts.

01

Create an account

Choose a username and a strong password. The server validates every field, hashes the password, and starts an authenticated session.

02

Sign in securely

Credentials are checked with bcrypt. If two-factor is enabled, a TOTP or single-use recovery code is required before the session is created.

03

Use the console

The dashboard shows account details, session state, and security activity. Enable 2FA, review your controls, and sign out when you are done.
